# Spec 06 — CI GitHub Actions, avec MOTIS et le test Joigny (phase 0)

> Rédigée le 2026-11-04. État : **appliquée le 2026-11-04 sur la demande de Brainditech (« fait ce qui a à faire et termine le correctement »), à relire dans la PR.**
> Branche : `phase-0/ci`. Une seule PR, plus une PR d'essai rouge jamais fusionnée (§7).
> Remplace la spec 01 (reportée par D34). Décisions liées : D22, D33, D34, D44. Invariants : 14, 15, 17. Risque : R8.

## 1. But

Chaque PR vers `main` et chaque poussée sur `main` lancent automatiquement :

- les vérifications de l'app (lint, types, tests, bundle Android) et du serveur (types, tests, dont les sha256 du manifeste, build) ;
- MOTIS v2.11.4 en `docker compose` chargé avec les fixtures figées, puis le test Joigny.

Cases de PLAN.md (phase 0) : « CI GitHub Actions », « Job CI qui lance MOTIS et le test Joigny », et la partie « vert en CI » de la case `fixtures/manifest.json`.

## 2. Décisions

Toutes celles de la spec 01 sont reprises (§2 de la spec 01), sauf l'absence de blocage de la fusion : depuis D52 (dépôt public), `main` est protégée et une CI rouge empêche la fusion. Ce qui change ou s'ajoute :

- **Deux jobs en parallèle dans un seul workflow** (`.github/workflows/ci.yml`) :
  - `verifications` : `npm ci` de l'app une fois, puis lint → types → tests → `npx expo export --platform android` ; ensuite `npm ci` du serveur, types → tests → build. Chaque étape est visible à part. Avant les types, la CI écrit `expo-env.d.ts` (`/// <reference types="expo/types" />`), le fichier qu'`expo start` génère en local et que git ignore : sans lui, `tsc` refuse l'import de `global.css` (TS2882, constaté sur la première exécution, puis en local en retirant le fichier).
  - `joigny` : import MOTIS (`docker compose run --rm motis-import`), puis `docker compose up -d --build --wait --no-deps motis api`, `/health` doit répondre 200 (`curl -f`), puis `npm run test:joigny`. En cas d'échec, les journaux des conteneurs sont affichés. `docker compose down -v` à la fin, toujours.
  - Écarté : MOTIS lancé dans le job `verifications` (un échec de MOTIS masquerait le résultat du lint et des tests, et le temps total s'additionnerait).
  - Écarté : MOTIS lancé comme `services:` de GitHub Actions (il faudrait recopier la configuration du `docker-compose.yml`, et le test ne prouverait plus que le compose du dépôt fonctionne).
- **L'import est une étape à part** plutôt que la dépendance `service_completed_successfully` de `up --wait` : son échec se voit sur sa propre ligne, et `--wait` n'attend alors que des services qui restent allumés.
- **Node épinglé à `22.23.4`**, la même version que l'image de l'API (`serveur/Dockerfile`), et non `22` comme le disait la spec 01 (invariant 17 : jamais une version flottante).
- **Actions épinglées par SHA de commit**, relevé le 2026-11-04 par `git ls-remote` (étiquettes légères, donc SHA du commit) :
  - `actions/checkout` v7.0.1 = `3d3c42e5aac5ba805825da76410c181273ba90b1` ;
  - `actions/setup-node` v7.1.0 = `949feb2413d6458794dcd2491c4babbbce0c15c1`.
- **Délais maximaux** : 15 min pour `verifications`, 20 min pour `joigny` (`--wait-timeout 300` pour le démarrage des conteneurs).
- **Toujours aucun secret** : ni Claude, ni Sentry, ni clé d'appareil. MOTIS ne sort pas du runner.

## 5. Case du PLAN réécrite (D33)

Avant :
> CI GitHub Actions (lint, types, tests, build), avec la fusion bloquée si rouge (protection de `main` à vérifier, R8). Preuve : une PR bloquée par une CI rouge volontaire.

Après :
> CI GitHub Actions (lint, types, tests, build) sur chaque PR et sur `main`. Pas de blocage technique de la fusion (D33) : on ne fusionne jamais en rouge. Preuve : une PR d'essai avec un test rouge volontaire, échec visible sur la PR (lien), jamais fusionnée ; puis la PR de cette spec, verte.

## 6. Sécurité

- `permissions: contents: read`, déclencheur `pull_request` (jamais `pull_request_target`) : une PR n'a ni secret ni droit d'écriture.
- Actions tierces épinglées par SHA. `npm ci` respecte les deux `package-lock.json`.
- Les ports de MOTIS et de l'API restent publiés sur `127.0.0.1` du runner seulement (`docker-compose.yml` inchangé).
- Aucune donnée de trajet personnelle : le test ne lit que les fixtures et le scénario Joigny.

## 7. Critères d'acceptation

1. Sur la PR de cette spec, les checks `verifications` et `joigny` sont verts, avec chaque étape visible séparément.
2. Une PR d'essai (`essai/ci-rouge`, une attente volontairement fausse dans `src/domaine/verdict.test.ts`) affiche `verifications` rouge à l'étape « Tests (app) ». Elle est fermée sans fusion, la branche est supprimée.
3. Le workflow ne contient ni `latest`, ni action non épinglée par SHA, ni secret.
4. La durée des deux jobs est relevée et consignée dans ETAT (budget de minutes, R8).
5. Le test Joigny échoue en CI si MOTIS ne démarre pas : l'étape `up --wait` ou `/health` est rouge, jamais un test sauté (déjà garanti par la spec 05 : MOTIS injoignable ⇒ échec).
